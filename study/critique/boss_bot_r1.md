## Исправления по влиянию

### 1. Блокер: рёв переносит героя через закрытую дверь арены

**Где:** `live/sim.js:1102`, ветка `e.mv === 'roar'`; `move`, строки 288–299.

**Причина:** рёв передаёт `M.push=150` одним вызовом `move`. `move` проверяет конечную точку перемещения по каждой оси, промежуточные клетки не проверяет. Одноклеточная стена/закрытая дверь остаётся между исходной и конечной позицией.

**Исходный зависший прогон seed35:** `/tmp/game-stuck35.bin`, `S.t=1281.1500000025073`; герой `(531.9579,1191.2771)`, клетка `[16,37]`; цель бота `exit[26,25]`. Арена `active:1, room:0, t0:905.7583333326739`, живой главный босс `hp:3287` остаётся внутри `(575.7370,876.9372)`. Все arena doors закрыты. Flow от выхода до героя равен `-1`.

**Локальное воспроизведение:** исходный checkpoint скопирован в `/tmp/review-checkpoint35.bin`, затем один короткий повтор с перехватом `SIM.step` остановлен в первый тик выхода из комнаты. Текущие параметры балансировки дают другое время встречи, но тот же дефект:

| Поле | Перед тиком | После тика |
|---|---:|---:|
| Время | 900.9916666660116 | 900.9999999993449 |
| Герой x | 911.8907682271192 | 919.7019708339775 |
| Герой y | 801.728764960881 | 951.52524393764 |
| Арена | active=1 | active=1 |

Комната арены `x16,y14,w18,h14`, южный край `y896`; дверь на клетках `y28` закрыта. Босс `(907.8468,724.1765)`, состояние `bwind`, приём `roar`. Герой за один тик проходит расстояние 150 px и оказывается южнее закрытой границы. Это дефект симуляции, а не выбор маршрута ботом и не потеря RNG при восстановлении.

**Однокадровый fixture:** `frames/study/escape35_before.bin`, V8-объект `{S,inp}` непосредственно до проблемного тика; описание/input в `frames/study/escape35_before.json`. Он проверен отдельным новым процессом:

```js
const fs = require('fs'), v8 = require('v8'), SIM = require('./live/sim.js');
const { S, inp } = v8.deserialize(fs.readFileSync('frames/study/escape35_before.bin'));
SIM.step(S, inp);
console.log(S.run.hero.x, S.run.hero.y);
// 919.7019708339775 951.52524393764
```

**Изменение:** проверять весь путь больших смещений в `move`, например шагами не более 8 px, сохраняя скольжение по осям. Добавить этот однокадровый случай в selfCheck и проверить выталкивание у каждой стороны запертой арены. Семена 80/104/120 имеют аналогичный итоговый stuck в исходной таблице, но этот раунд не приписывает им ту же причину без индивидуального перехода.

### 2. Существенно: stuck/timeout проходят приёмку баланса

**Где:** `tools/difficulty.cjs:82–85`, `check`; `tools/bot.cjs:166,223`.

`stuck` лишь печатается в таблице; `check` принимает его как обычный проигрыш. Более того, незавершённый этаж отсутствует в `cur.floors`, поэтому seed35 не попадает в знаменатель метрик босса8 и давления этажа8, хотя встреча уже шла.

**Тест без ботов:** `/tmp/review-count-stuck.json` содержит expert seeds1–2, один win и один stuck, построенные из готовой строки результата. Команда заканчивается кодом0 и `every band met`:

```sh
node tools/difficulty.cjs --from-json /tmp/review-count-stuck.json --seeds 1-2 --profiles expert --diff hard --check
```

**Изменение:** валидатор результатов обязан отклонять stuck/timeout перед диапазонами баланса. Для диагностики можно сохранять текущий незавершённый этаж с признаком incomplete; его метрики не должны молча считаться законченным боем.

### 3. Существенно: число строк не подтверждает покрытие seed и runs

**Где:** `tools/difficulty.cjs:84`; загрузка `--from-json` 135–136; resume 14–18.

Проверяется только длина массива первого run для профилей с BANDS. Две строки seed1 могут заменить seed1+seed2. Остальные запрошенные runs не проверяются на полноту. Повторные источники `--from-json` просто конкатенируются.

**Тест без ботов:** `/tmp/review-count-duplicates.json` содержит два seed1 и не содержит seed2, один результат win и один dead. Та же команда с этим файлом даёт код0 и `every band met`.

**Изменение:** отдельно проверить каждый запрошенный профиль, точное множество seed, отсутствие дублей и наличие всех runs в каждой строке; после этого считать диапазоны. Это также обнаружит частичные строки resume до смешивания их с заново полученными результатами.

## Что проверено без замечаний

- Snapshot делается на границе этажа после сброса `given/chased/seen`, до распределения очков, экипировки и следующего шага ввода. Поэтому пустые восстановленные коллекции соответствуют моменту сохранения.
- V8 сериализует `S` и `vars` одним графом, сохраняя ссылки `focus`, героя и прочих объектов; JSON-склейки здесь нет.
- Состояние RNG возвращается перед следующим решением; ранее выполненный ведущим побитово совпавший replay seed9 floor8 согласуется со структурой кода. В этом раунде этот полный повтор не запускался ещё раз.
- При восстановлении проверяются seed/profile/diff и runs=1; ретюнинг hp босса сохраняет долю здоровья, dmg пересчитывается по текущим данным.
- `--replay-floor` сохраняет законченные результаты, не достигшие изменяемого этажа; достигшие перезапускаются. При отсутствии файла snapshot выполняется полный прогон.
- `B` захватывается до `SIM.step`, поэтому смена этажа тем же тиком не теряет ссылку на побеждённого босса. `boss.died` фиксируется в момент завершения боя; последующая смерть на этаже не меняет завершённую встречу.

## Правила и мелкие замечания

Нарушены принципы ref2game «пользователь не первый находит проверяемый дефект» и детерминированной приёмки: закрытая арена не удерживает героя, а ошибочные измерения могут считаться валидными. Нужны локальный инвариант перемещения и отдельная проверка полноты данных.

Сохранённые строки не содержат идентификатор версии параметров. Поэтому корректность смешивания старых префиксов и новых этажей зависит от дисциплины запуска: повтор с floor8 допустим при изменениях, которые не влияют на floor1–7. Это ограничение следует явно документировать; само по себе оно не блокирует текущую схему ускоренного ретюнинга.
