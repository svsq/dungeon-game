## 8. Требования к архитектуре порта

Вытекают из находок; номера `R-n` использованы выше.

**R-1. Логика — отдельная сборка C# без ссылок на Godot.** Сборка `Sim` (+ `Dungeon`, `Data`) не знает про `Godot.*`, время, сцену, `Random`; отрисовка читает её только через запросный слой (аналог `SIM.Q`). Правило `layercheck.cjs` (T-27, T-23) становится ошибкой компиляции, а не проверкой по регулярным выражениям; пункты вроде `hud_kit.js` без класса невозможны. Тесты `Sim` запускаются без редактора (`dotnet test`).

**R-2. Один вход проверок.** Реестр проверок (атрибут `[Check(domain, speed, kind)]` или список в данных), запуск `check --fast|--slow|--only domain`, единый формат отчёта (JSON, код выхода, имя и значение порога), запуск в CI и перед релизом. Сегодня автоматически бежит одна проверка из 50 скриптов (T-01), четыре красных на чистой ветке (T-03). Вид «измерение» (`playtest`, `hazwalk`, `frameprof`) отделён от вида «проверка с вердиктом» (T-11).

**R-3. Детерминизм sim — отдельный контракт.** Шаг 120 Гц, целые сиды, **одна** реализация ГСЧ с тестовыми векторами (сейчас три копии, T-21), правила: порядок обхода коллекций определён (в JS ключи объектов идут по вставке; в C# `Dictionary` и `HashSet` не гарантируют ничего без явной сортировки), сортировки устойчивые, тригонометрия и `Math.Pow`/`Atan2` не должны менять результат: либо допуск в эталоне (1e-6), либо таблицы. Побитовое равенство с JS недостижимо и не требуется; нужны допуски по полям и сверка статистик (раздел 7.2).

**R-4. Вход — запись и воспроизведение.** Структура ввода (ключи, указатель `px/py`, `click`, `left/right/up/down`) пишется в журнал и подаётся на любой шаг; эталон sim строится на записях, а не на живом боте (T-24б). Раскладка кнопок и экранов интерфейса доступна sim как данные (`DATA.UI.*`), чтобы бот и тест нажимали кнопки без отрисовки (`bot.cjs` кликает по прямоугольникам `D.UI`).

**R-5. Явный запросный интерфейс для ботов.** Бот и скрипты сценариев пользуются конечным списком операций (сейчас 29 членов `SIM` и ≈ 45 полей `DATA` у `bot.cjs`, остальное читается из состояния напрямую и ломается при любой смене формы состояния). `IBotView` — часть контракта sim; бот и баланс (кривые, `BANDS`) работают поверх него.

**R-6. Золотые файлы в git и читаемые расхождения.** `tests/golden/` с каноничным JSON (ключи по алфавиту, числа с фиксированной точностью), генератор один и для JS-эталона, и для C#-прогона; при расхождении печатается первый различающийся путь (`run.hero.hp @ step 14210`), а не «хеш не совпал» (T-24г). Каталог вне `frames/`.

**R-7. Данные как файлы, ключи текстов проверяются.** Контент (враги, предметы, биомы, `BAL`, `BANDS`, профили бота) в JSON/ресурсах, читаемых и игрой, и инструментами; `docs/names|notes|talk` уже такие. Тексты: таблица ключей (CSV/PO) и тест «ключ использован, не лишний, форма множественного числа, подстановки `{@name}`, пара `@pad`» (аналог `textcheck.cjs`).

**R-8. Тестовый harness отрисовки.** (а) Фикстуры (замена QA-состояний) собираются **по имени**, лениво (T-14), и несут теги и поле `covers`; тест реестра печатает «состояния без проверки» (T-13). (б) Рендер в заданный момент `t` от состояния — чистая функция (`render = f(t, state)`), чтобы первый кадр не отличался от пятого (задача 2013 — кэши в отрисовке) и можно было автотестом сравнить два кадра. (в) API следа суставов по идентификатору актёра (замена `LIB.TRACE`): позиции суставов на кадр, на нём строятся проверки движения. (г) Одна точка перехвата отрисовки (вызовы, контурные копии, плоские фигуры), чтобы подсчёт не терял пути (T-19). (д) Экспорт прямоугольников интерфейса и якорей (`__UI`, `__ANCHORS`) для проверок перекрытий (`hudzone`, `brawlcheck`, `qa.mjs`). (е) Снимок кадра на сервере без GPU или с `xvfb` — решение прототипа 2053.

**R-9. Фабрика сценариев в sim.** Сегодня 20 скриптов собирают врагов, сундуки и комнаты по 20 полей вручную (T-29) и повторяют подготовку сцены (T-16). Нужен `ScenarioBuilder`: `NewRun(mode, seed)`, `EnterFloor`, `SpawnEnemy(type, pos, overrides)`, `GiveItem`, `Teleport`, `Step(n)`, `Clone()`. Состояние должно дёшево глубоко копироваться: checks клонируют его (`structuredClone`) по несколько раз на кадр.

**R-10. Данные ригов.** Опорные точки и иерархия частей (сейчас `live/rigs.js`) — в JSON, из которого собирается `Skeleton2D`/сцена; значения порогов движения (`HAND_MAX`, `FLINCH`, `GLIDE` …) — таблицей данных, не константами в коде проверок (раздел 7.1).

**R-11. Звук.** Заглушки; событие несёт материал и ключ, и это проверяется в sim (`reactionCheck`); офлайн-рендер звука (`lavaaudio`, `cavereactionaudio`) не переносить.

**R-12. Сохранение с версией формата.** Сохранение и продолжение — отдельные тесты на каждый режим (`caveresultcheck`, `cavemapcheck`, `sim_checks.js:3571` показывают, где ломается: потеря `seen/rseen`, зума, `ambushRolled`). Миграции — тестовые файлы старых сохранений.

**R-13. Ввод по физическому коду клавиши.** Служебные клавиши (пауза, шаг, скорость) не зависят от раскладки; тест ввода в поле имени с российской раскладкой (`namekeys.mjs`).

**R-14. Зависимости инструментов лежат в репозитории.** Сегодня 32 скрипта берут Playwright из `~/.claude/skills/ref2game/scripts/node_modules` по вшитому пути, `package.json` в проекте нет; Python-инструментам нужны `numpy`, `Pillow`, `scipy` без списка. В порте: файл проекта (`.csproj`, `Makefile`/`just`), `requirements.txt` для артов, один загрузчик (T-17).

**R-15. Счётчики производительности и утечек в игре.** Время кадра CPU и GPU, число вызовов, память текстур, число живых целевых буферов и сирот узлов выдаются как данные (замена крючков `frameprof.mjs` на `WebGL2RenderingContext`); тест «после смены этажа числа возвращаются к исходным ±допуск» (то, что 2040 будет мерить руками, делать автоматическим).

**R-16. Кеш баланса.** Ключ — хеш сборок `Sim` и данных, без файлов проверок (T-26); результаты бота пишутся построчно (как `balance-cache`) и сверяются повторным прогоном 5 % (механизм `difficulty.cjs:227-242` стоит сохранить).

**R-17. Режимы — ось тестов.** `campaign`, `town`, `cave`, `magma`, `endless` и сложности: любой эталон и любой тест принимает режим параметром (в `samecheck.mjs:32` режимы перечислены вручную, в `difficulty.cjs` и `bot.cjs` ещё раз).

**R-18. Границы сборки инструментов и релиза.** В релизную сборку не попадают ни тесты, ни `tools/`; проверки, которым нужна отрисовка, не вызываются из sim-проверок (T-23).
