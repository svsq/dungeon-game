## 2. Требования по слоям

### 2.1 Симуляция и данные

- Сим, данные и генератор: чистый C# без `Godot.*`, без времени, `Random` и сцены; тесты идут без редактора, `dotnet test` (sim P-8, P-11; tools R-1; dungeon R1; scene п.1; 2052).
- Граница слоёв: отдельные сборки (Sim, Dungeon, Data, общая сборка запросов к карте, туману и `LIGHT_R`); ошибка компиляции вместо `layercheck.cjs` по регулярным выражениям (tools R-1; dungeon R13).
- Шаг фиксированный, 120 Гц; сид забега приходит снаружи (sim P-1; tools R-3).
- Один ГСЧ: mulberry32 на `uint` с `unchecked`, `peek` отдельным потоком, `qhash` и `mix32` без изменений; одна реализация с тестовыми векторами вместо трёх копий (sim P-1; tools R-3; data А-5; dungeon R3).
- Реестр потоков ГСЧ одной таблицей, счётчик бросков и имя потока, единственные способы броска `Ri`, `Chance`, `Pick`, `WeightedPick`, `Shuffle`, `Skip(n)` (dungeon R3).
- Целочисленный хеш вместо `Math.sin`-хеша `henRnd`; один детерминированный хеш общий для сима и вида (sim P-1; scene п.12).
- Свои `Vec2` и `double` для позиций и скоростей; `Vector2` Godot (`float`) в ядро не пускать (sim P-1).
- `JsRound` (.5 вверх), устойчивые сортировки, явное целочисленное деление и деление на ноль (sim P-1; tools R-3; dungeon R5).
- Порядок обхода коллекций определён явно: у `Dictionary` и `HashSet` порядка нет, упорядоченные `OrderedSet`, `OrderedMap`, `StableSort` (tools R-3; sim P-7; dungeon R5).
- Сравнение с JS: целочисленные поля (id, счётчики, хп) точно, `double` с допуском (sim P-1; tools R-3, допуск 1e-6).
- расхождение: sim P-1 и data А-5 требуют бит-в-бит для целочисленной части, хешей и `mix32`, `bagOrder`, `layOf`, `modOf`, `wanderAt`, `stageOf` как обязательное условие приёмки; tools R-3 пишет, что побитовое равенство с JS недостижимо и не требуется; решение игрока 14.11.2026 снимает его с сохранений и оставляет только эталонным тестам с допуском.
- Профиль забега `RunProfile { Mode, ViaTown, Demo, Test, Difficulty, Class, Kit }` создаётся один раз, флаги `S.demo`, `R.test`, `R.viaTown`, `R.mode` не разбросаны (sim P-2).
- Шина сигналов `Hit`, `Kill`, `Hurt`, `Pickup`, `FloorEntered`; подписчики `Quests`, `Meta`, `Journal`, `Powers`; порядок подписчиков фиксирован и записан (sim P-3).
- Поток событий для вида отдельный и логику не двигает; события несут `Id`, а не индекс (sim P-3, P-7).
- Шаг как конвейер систем в фиксированном порядке, записанном таблицей; ранние выходы (смерть, уход с этажа, заморозка) — состояния героя, не `return` посреди функции (sim P-6).
- Сущности по `Id` (замок, секрет, паутина, алтарь, декор); «никогда» (`-9`, `-1e9`, `undefined`) — типизированное поле с одним `NEVER` (sim P-7).
- Типизированная схема состояния (около 100 полей `R`, 100 героя, 160 монстра, 50 карты); мета-настройки вида (`zoom`, `mute`, `bright`, `gfx`, `trkFold`) отдельно от прогресса (sim P-12).
- Горячий путь без выделений: числовые ключи, кеш статов с версией героя, кеш препятствий с версией карты `m.rev`, пространственная сетка, удаление на месте, пулы снарядов и огней (sim P-5; М-3, М-4).
- Проверка нуля выделений в шаге без событий: `GC.CollectionCount` на трассе из 1000 шагов (sim P-5; М-3).
- Шаг сима не оптимизировать заранее; бюджет в тесте не больше 0,5 мс на Deck (М-2; sim P-17, мс на 1000 шагов на пещерах и магме).
- Версии состояния вместо строковых ключей на кадр (М-4; scene п.9, п.10).
- Вход — намерения `InputFrame { Move, Aim (мировая точка), Buttons, Slot, Interact }`, без пикселей и кодов клавиш (sim P-9; hud п.2, п.5; data А-6).
- Сим не знает пикселей: экран шлёт команду по id (`buy:3`, `eq:helm`, `slot:2`, `Pressed(id)`, `Back`, `Page`, `Drag`), сим отдаёт модель вида на экран; 59 `SIM.Q.*` становятся методами модели (hud п.2; data А-6; sim P-9).
- Один фасад чтения `IWorldView`; чтение не пишет состояние (sim P-11).
- Туман: `seen` и `rseen` — состояние (сохраняется); овалы, шум и «закрытые карманы» — правила представления (sim P-10).
- Презентация вне сима: камера, тряска, фазы шага, следы краба, походка (`stepLen`, `h.gp`) считаются в узлах из событий и позиций (sim P-8).
- Не копировать код построчно; поведение задают проверки, комментарии с `TASKS NNN` не переносить (sim P-13; scene п.13).
- Реестры вместо общих списков: сила, событие, монстр, предмет, экран, проверка — файл рядом и автосбор; общий список не правится (sim P-16; hud п.1; data В-1; tools R-2).
- расхождение: sim P-16 и hud п.1 предлагают регистрацию атрибутом и поиском по сборке или каталогом ресурсов; prototype ш.1 (риски) предупреждает, что NativeAOT на iOS опирается на рефлексию и обрезка сборок может её ломать.
- Данные в JSON одним скриптом `tools/export_data.cjs` над собранным `DATA` (после спредов и мутаций); скрипт проверяет полноту; после заморозки JS источник правды JSON (data А-1; sim P-12; tools R-7).
- Функции в таблицах данных становятся формулами с параметрами или классом `Balance` с тестами (data А-2).
- Ссылки по id проверяются при загрузке данных; id уникальны, в том числе при слиянии даров, сил и реликвий; для фиксированных множеств типизированные id (data А-3, В-2).
- Мини-язык сил (22 `fx`, 21 `trig`, 6 `if`) как перечисления и таблица обработчиков; данные сил остаются JSON (data А-4).
- Геометрия ригов (`colossusStepAt`, `BOSSES.boss_colossus.step`) берётся из экспорта ригов, не числами в данных (data А-7).
- Мёртвое (`ELITE.guard*`, `plural`, путевые камни, дубли `PROP_MAT`) убрать до экспорта данных (data А-10).
- `data_ui.js` не переносится: раскладка живёт в сценах Godot (data А-6; hud п.3).
- Записки, реплики и имена из `docs/*.json` читаются лениво по эпохе (898 записок, 293 тыс. знаков); число вариантов в массивах не считается постоянным (data А-9).
- Тексты через `tr()` и `TranslationServer`, формат CSV или PO по доменам (выбор за 2052); ключи из id сущностей; смена языка без перезапуска (data Б-1, Б-2; hud п.13).
- Плейсхолдеры именованные; числа и проценты форматирует локаль; множественное число целой фразой по правилам языка; род и склонение в данных (data Б-3, Б-4, Б-5).
- Подсказки клавиш токенами действий (`{act:inventory}`, `{interact}`), глиф подставляет слой ввода; 69 двойников `@pad` исчезают (data Б-7; hud п.7).
- Числа в описаниях сил берутся параметрами; тест «нет цифр вне параметров» (data Б-8).
- Глоссарий `NAME.*` с `{@имя}` разворачивается один раз при загрузке, цикл запрещён, неизвестное имя ловится при сборке ресурсов (data Б-9).
- Тестовые и отладочные строки (24) вне игровых ресурсов перевода; нет ключа в языке — падение на русский с подсчётом пропусков в тесте; шрифт с покрытием `×−…·«»` (data Б-10, Б-12, Б-11).
- Рельсы города и имена элит считать при загрузке этажа и при спавне, не каждый кадр (data §10).

### 2.2 Генератор этажей

- Отдельная сборка `Gen` без Godot, только `int` и `double`; `genFloor` — чистая функция `(seed, floor, GenOptions, Data)`, без статического изменяемого состояния, потокобезопасна (dungeon R1).
- Генерация на фоновом потоке: до 60 повторов не должны дёргать кадр; смена этажа в фоне с экраном загрузки, кадр не длиннее 33 мс (dungeon R1; М-7).
- Типизированные результаты стадий вместо `GF` (`RoomsOut`, `LinksOut`, `TerrainOut`, `FillOut`, `Events`), `StageSpec` и `GenOptions` (боевые поля отдельно от крючков QA); порядок вызова в одном месте; `Room.Id == index` проверять на выходе (dungeon R4).
- Типы объектов карты (`Room`, `Enemy`, `Chest`, `Pot`, `Trap`, `Torch`, `Decor`, `Door`, `Secret`, `Crossing`, `Hazard`, `FloorMap`); флаги `int?` и `bool?` там, где в JS значим 0; словарь полей составить grep-ом до начала (dungeon R7).
- Данные генератора одним экспортом из JS (JSON, порядок ключей сохранён): 25 имён и функции `stageOf`, `rosterAt`, `wanderAt`, `wayFloor`, `runOf`, `hazIn`, `hazAxes`; таблицы биомов из кода и `LIGHT_R` сначала переезжают в данные (dungeon R6).
- Алгоритм при переносе не менять: порядок бросков, сортировок и проверок отказа — часть формата карты; чистки делались в JS до порта под `samecheck --only gen` (dungeon R11).
- Скорость: сетки на `int`-индексах вместо строковых ключей, `roomId[W*H]`, битовые маски, пул буферов BFS на стадию, `PriorityQueue` для `RouteRiver`; порядок обхода сохраняется (dungeon R10).
- `GenResult` возвращает номер принятой попытки и причины отказов по кодам (по каждому `return null`) (dungeon R15).
- Проверки этажа (связность, ширина переходов, число переправ, `rewardsOf`, `riverOk`) — тесты над `FloorMap`, а не часть генератора (dungeon R14).
- Общие библиотеки (запросы к карте, туман `fogHash` и `fogNoise`, `LIGHT_R`) лежат в общей сборке, не в `Gen` (dungeon R13).
- Эталоном для порта служит карта после очистки JS (2047, 2048); F-01 меняет карту и снимается отдельным эталоном (dungeon R11).
- Поля `rugs`, `ambush`, `loose`, `way: null` не переносить (игрок 14.11).
- расхождение: dungeon R2 требует слой `JsMath` (fdlibm и `hypot` из V8, золотые векторы ≥10⁶ на функцию, побитово на всех платформах) «первым делом» и «обязательно навсегда» при варианте `diff` (dungeon R9); решение игрока 14.11.2026 снимает это для сохранений, оставляя допуск в эталонных тестах.

### 2.3 Сохранения

- Версия формата в каждом сохранении (`R.v`), миграции шагами `v → v+1` только при загрузке, не на каждом шаге (sim P-4; tools R-12; игрок 14.11).
- Сохранения JS не читаются, импортёра нет; в заметках к релизу указать (игрок 14.11; расхождение: sim P-4 «либо один импортёр, либо не читаются», data А-8 «сказать, что делать со старыми», tools R-12 «миграции — тестовые файлы старых сохранений»; решено в пользу «не читаются»).
- Этаж сохраняется целиком (карта и состояние), генератор при загрузке не вызывается (игрок 14.11).
- расхождение: sim P-4 предлагает `FloorLayout` из генератора отдельно от `FloorState` и сохранять только `FloorState`, dungeon R9 оставляет вариант `diff`; решение игрока выбирает карту целиком; деление на `FloorLayout` и `FloorState` как типы остаётся вопросом (раздел 3).
- В сохранение попадают id, версия данных и сид; тексты и пиксели не попадают (data В-4, Б-6, А-6).
- Состояние и события не хранят готовых строк: прозвище элиты, заголовок квеста, `S.ev.s` — id и параметры (data Б-6).
- Версия данных своя вместо `GEN_VERSION` (34) и `ITEM_BAL.version` (2) как признаков совместимости (data А-8).
- Журнал баланса (`R.log.fl`) вне записи и с границей; один слот на файл (sim P-4; М-6).
- Запись атомарная (временный файл и переименование) и вне кадра; ошибка записи видна игроку (sim P-4; М-6).
- Размер для ориентира: запись забега до 0,48 МБ на 15-м этаже, `stringify` 0,3–2,3 мс; пять заполненных слотов не собирались (summary §2, §5).
- Тесты сохранения и продолжения на каждый режим; ловить потерю `seen/rseen`, зума, `ambushRolled` (tools R-12, R-17).

### 2.4 Отображение

- Слои как именованные `CanvasLayer` и `SubViewport` (земля, декали, полоса актёров, свет, эмиссия, оценка, HUD); явные `z_index` вместо ключей-костылей (`1e8`, `y - 1000`) (scene п.3).
- Y-сортировка движком, начало узла у ног; ящики, бочки, герой и враги прямые дети узла мира (scene п.3; prototype ш.2).
- Два разрешения: мир на сетке 2×2 (`SubViewport` 960×540, nearest), свет и HUD гладкие; склейка полноэкранным шейдером; `ZOOM` 0,5–1,5 и рамка 16:10 закладывать с начала (scene п.4).
- Что подтвердил прототип: `SubViewport` 960×540 nearest работает просто и дёшево; рамка 16:10 и масштаб `ZOOM` не проверялись (prototype ш.2).
- Решить до остального пайплайна: П1 (вращающиеся части nearest или перерасчёт голосованием) и П2 (карта света пятнами или `PointLight2D`) (scene п.7).
- События вместо частиц: эффект запускается записью `{kind, t, pos, params}` и рисуется по возрасту `GT - t`; для повторяемых кадров время подаётся своим `uniform`, не `TIME` (scene п.2).
- Свет — таблица источников (цвет, радиус, мерцание, вид) и одна функция сборки; без второго CPU-расчёта света на актёрах; `LightField.Sample` только для логики; категории через `light_mask` и материалы (scene п.5).
- Шейдеры (около 20) по файлам `.gdshader`, общие куски (`hash`, `vnoise`, `fbm`, `stepped`, `fxq`) через `#include`, варианты через `#define`, `u_t` заменить явным uniform (scene п.6).
- Ресурсы по биомам, не 631 МБ на старте: сжатие VRAM (ETC2 и ASTC на мобильных, BPTC и S3TC на ПК), атласы по биому и по классу героя, выгрузка при выходе из забега, `SIZES` в параметры импорта (scene п.8; М-9).
- Ориентир к М-9: сейчас около 0,9 ГБ текстур постоянно (908 МБ на этаже 1) (М-9; summary §1).
- На Android экспорт требует `textures/vram_compression/import_etc2_astc=true` (prototype ш.1).
- Маски карты (`lava`, `water`, `cave`, `top`, `veins`…) — малые `ImageTexture` R8 и RGBA8 с билинейной выборкой, обновление по версии карты, окно `cellsChanged` сохранить (scene п.9).
- Туман войны маской клеток от сима с версией, не хеш на кадр (scene п.10; М-4). В прототипе тумана с памятью клеток нет (prototype ш.2).
- Риги: узлы по частям, шарниры из той же таблицы (`rigs.js` как данные ресурса), позы кодом по часам атаки сима, двухкостный IK писать своим (scene п.11; tools R-10).
- Мягкие кости привидения и зверей через `Polygon2D` и `Skeleton2D` (инструмент из `softbones.json`); в прототипе не собраны (scene п.11; prototype ш.2).
- Сцену рига собирать из JSON с пороговыми числами движения (`HAND_MAX`, `FLINCH`, `GLIDE`) таблицей данных (tools R-10).
- Главный риск: риг из 12 отдельных текстур даёт около 12 draw calls на врага; части складывать в атлас (по типу), проверить, что Y-сортировка склеивается; гипотеза не проверена (prototype ш.2; М-1).
- Бюджет: около 2500 draw calls на кадр при 60 FPS на iPad 6 и Pixel 7, 1250 как запас; спрайт без рига на толпу стоит почти ничего (prototype ш.2).
- Бюджет вызовов отрисовки на кадр, пакетирование (М-1; scene п.17).
- Обводка и ауры одним проходом (М-1); шейдером на спрайте, а `CanvasGroup` не на каждого монстра, максимум на выбранную цель (М-1; prototype ш.2).
- расхождение: scene п.11 предлагает обводку и ауры шейдером по `CanvasGroup`, одна группа на актёра; prototype ш.2 (вывод 6) и М-1 советуют не ставить `CanvasGroup` на каждого монстра; сам `CanvasGroup` не измерен.
- расхождение: scene п.4 и п.5 хотят свет гладким отдельным от мира (два буфера, `light_mask`); prototype ш.2 нарисовал свет внутри вьюпорта 960×540, он ступенчатый, и «два буфера» остаются риском 2052.
- Базовый рендерер Compatibility (OpenGL ES 3.0 на iPad 6); Mobile на A10 не поднимается (Metal 3), для новых устройств возможное дополнение, не проверено (prototype ш.1, ш.2; игрок 14.11).
- Свет на Compatibility почти бесплатен: 7 `PointLight2D` плюс `CanvasModulate` не меняют число draw calls; теней, больше 7 источников и света разного размера не пробовали (prototype ш.2).
- Режимы качества для мобильных: свет пятнами или без обводки на низкой, текстуры по размеру экрана; блум и `CanvasGroup` проверять на Android и iOS первыми (scene п.17).
- Пост-проход (оценка, виньетка, дизеринг, блум), FX заклинаний и HUD в замеры прототипа не входили (prototype ш.2, п.4).
- Первый запуск на устройстве холодный (компиляция шейдеров, 57–59 FPS против 60): его не брать как замер (prototype ш.2).
- Картинка шейдеров лавы, воды, магмы и пещеры сверяется с эталоном по кадрам, а не `samecheck` (scene п.18).
- Правила картинки (цвета огня, лифты, пороги, режимы графики) в ресурс «стиль» (scene п.13).
- Явная очистка `Scene.Release(run)` при выходе из забега и смене этажа (карта, маски, цели) (scene п.15).
- Без глобальных слотов: контекст кадра и состояние прохода параметром или сервисом с областью жизни кадра (scene п.16).

### 2.5 HUD и ввод (клавиатура, геймпад, сенсор)

- Навигация стеком `ScreenStack.Push/Pop` вместо строки `S.screen` (hud п.1).

- Прицел из оси или указателя без эмуляции мыши; автоцель опция (мобильные, Deck); `power` одно действие для правой кнопки и L2 (hud п.8 и заметки).
- Подсказки по фокусу и долгому нажатию, не только по наведению мыши (hud п.9).
- Слои: игровой HUD, окна, оверлей ввода (сенсорные органы), оверлей подсказок, отладка — отдельные `CanvasLayer`; мобильные органы над HUD без правок экранов (hud п.11).
- Масштаб: базовый 1920×1080, `canvas_items` и `expand`, якоря, отдельный множитель UI, безопасная область, минимальная цель касания и кегль; проверка на Deck 1280×800 и телефоне (hud п.12).
- Поле имени `LineEdit`, экранная клавиатура на мобильных; допустимые символы остаются в данных (hud п.15).
- Режим «взять и положить» (`S.drag.carry`) один в симе для клавиатуры, геймпада и касания (hud, заметки к порту).
- Окно обновления и полноэкранный режим платформенные, на мобильных не нужны (hud, заметки к порту).
- Сенсор (R-47): виртуальный стик или касание для хода, кнопки умений и зелий, раскладка под разные экраны; раскладка и размеры не влияют на состояние (R-47; sim P-9).

- Тесты текста: ключ использован, не лишний, формы множественного числа, `{@имя}` существует, нет кириллицы вне текста, нет цифр вне параметров; `fx/trig/if` известны, ссылки по id целы (data В-2; tools R-7).
- Раскладка проверяется по `get_global_rect()` узлов; автотест достижимости всех кнопок стрелками и возврата по `ui_cancel`; список ручных сценариев для Deck и телефона (hud п.16).
- Модели вида и команды экранов тестируются в C# без Godot (hud п.16).
- Harness отрисовки: фикстуры по имени с тегами и `covers`; `render = f(t, state)`; API следа суставов по id актёра; одна точка перехвата отрисовки; экспорт прямоугольников UI и якорей; снимок кадра без GPU или `xvfb` — решение прототипа (tools R-8; scene п.14).
- Тест «после смены этажа числа живых текстур, целевых буферов и узлов возвращаются к исходным ±допуск» на трассе 16 этажей × 3 прохода; автоматический вместо ручных замеров 2040 (М-8; tools R-15; scene п.15).
- `profile.mjs` как тест бюджетов; кадры снимать под синхронизацией; GC и кадр в одном отчёте (М-11; sim P-17; tools R-15).
- В 2053 и далее CPU и GPU мерить раздельно штатными средствами Godot, раньше на Deck, а не на машине разработки (М-10).
- расхождение: М-10 ждёт раздельных CPU и GPU штатными средствами; prototype ш.2 («Ловушки») показал, что на Compatibility `gpuRender` и `Performance.Monitor.TimeProcess` дают нули или мусор, GPU-время оценено косвенно по `script + cpuRender`.
- Метод прототипа (счётчик `drawn=` доли отрисованных кадров, запись в `bench.txt`, прогон по этапам, `--stress`) переходит в порт (prototype ш.2, вывод 7).
- Предпосылка: цепочка 2041 → 2044 → 2045 → 2047 → 2048 → 2052 закрыта до архитектуры, эталоны сняты с неизменённого JS (summary §3; sim P-14).

### 2.8 Инструменты и бот

- Бот на C# с теми же профилями, подключённый к симуляции как библиотека; доли побед и смертей сверяются с JS-ботом на одних сидах (2052).
- Требования замороженных 360, 369, 372, 1727, 1386 переходят в проверки порта: отчёты «умение × число применений» и «событие × доля забегов × смертей», кривая побед по Жару, эксперт сильнее среднего, прохождение карты ботом (2052).

- расхождение: tools R-4 даёт симу раскладку кнопок как данные (`DATA.UI.*`), чтобы бот нажимал кнопки без отрисовки; sim P-9, hud п.2 и data А-6 требуют, чтобы сим не знал пикселей и принимал команды по id.

- Пайплайн арта (`art/gen`, промпты, `prep.py`, rig-скрипты) остаётся источником арта; в Godot копируются части и текстуры (prototype ш.2, копии, не симлинки).

### 2.9 Сборка и выпуск

- Экспорт Godot на Android, iOS, Windows, Linux одной консольной командой; .NET встроен в экспорт Windows и Linux (prototype ш.2).
- Android: Mono, .NET 9.0.23, arm64-v8a, minSdk 24, gradle не нужен; эмулятор с 16 КБ страницами собирается; debug APK 104 МБ, release не измерен (prototype ш.1).
- iOS: NativeAOT, экспорт только с macOS; debug `.app` 128 МБ; симулятор на Apple Silicon не годится (шаблон только x86_64); Xcode 27 собирает от iOS 15.0 (prototype ш.1).
- iOS NativeAOT опирается на рефлексию Godot; рост кода C# может ломать обрезку сборок; проверка на iPad при каждом заметном шаге (prototype ш.1, риски).
- Статус C# для Android и iOS в Godot 4.7.2 по документации «experimental»; на практике работает; проверить заново при выборе версии (prototype ш.1).
- Личная команда Apple: профиль живёт 7 дней, до 3 приложений на устройстве; для долгих замеров и App Store нужна платная команда (prototype ш.1, риски).
- Release-сборки обеих платформ, их размер, экспорт Windows 10 и Linux в запуске не проверены (prototype ш.1, ш.2).
- В заметках к релизу на Godot: старые сохранения не переносятся (игрок 14.11).
- Обновления вместо `electron-updater`, подписи, судьба JS-версии на время порта (релизы, новые фичи) входят в архитектуру, но решения в источниках нет (2052; раздел 3).
- Правила магазинов (Google Play, App Store: аккаунты, возрастные рейтинги) отнесены к R-47 (R-47).

### 2.10 Производительность и память

- Кадр упирается в CPU (подача draw calls), не в GPU: цена вызова около 4,4 мкс на iPad 6, 3,9 на Pixel 7, 3,1 на M3 Max (prototype ш.2, вывод 1).
- Ориентир по кадру Steam Deck: те же JS-сцены на Deck в 4–5 раз дороже (18–22 мс на этаже 10) (М-12; summary §1).
- расхождение: М-10 и М-12 берут Steam Deck ориентиром и просят мерить на Deck раньше машины разработки; решение игрока 14.11.2026 ставит Deck на потом, а замеров на Deck в прототипе нет (prototype ш.2, «Не получилось»).
- Замеры прототипа (debug, Compatibility): Pixel 7 держит 60 FPS до 400 ригованных врагов; iPad 6 60 FPS до 200 и 35 FPS на 400; 200 врагов занимают 12–13 мс из 16,7 (prototype ш.2).
- Ориентир нагрузки: около 70 монстров на экране в играх, по таблицам прототипа 6–9 мс на `script + cpuRender` без поста, FX, HUD и сима (prototype ш.2, вывод 4).
- C# не узкое место: скрипт 0,1–3,8 мс (iPad NativeAOT 2,5 мс на 200 врагах), куча C# 6–21 МБ, заминок GC не видно (prototype ш.2, вывод 5).
- Ноль выделений в горячем пути, `struct` и пулы, проверка `GC.CollectionCount` (М-3).
- Подписи как пул узлов по `id` события; индекс в `S.ev` устойчивый (М-5; summary §2).
- Текстуры по биомам и со сжатием вместо около 0,9 ГБ постоянно (М-9).
- Смена этажа не длиннее 33 мс на кадр; вход в магму 150–356 мс, на Deck 0,15–1,5 с (М-7; summary §1).
- Кучи и текстур не растёт на трассе 16 этажей × 3 прохода (М-8).
- Память-ориентир прототипа: Pixel 7 PSS 553 МБ (400 врагов), `static` Godot 74–98 МБ, видеопамять Godot 66–80 МБ (prototype ш.2).
- Не измерены: Steam Deck, слабый Windows-ПК, тепло iPad 6 и Pixel 7 при долгой нагрузке, батарея, release-сборки, тяжёлый бой и босс (prototype ш.2; summary §5).

## 3. Открытые вопросы игроку для 2052

1. Прототип `elderdeep-godot` идёт в основу порта или выбрасывается? Варианты: основа (метод замера и поза рига уже есть); выбросить, оставить только метод замера; взять риг-код и сцену, перебрать остальное (prototype ш.2, вывод 7).
2. Рига как атлас: один атлас на тип монстра, один общий, или спрайт без рига на толпу на расстоянии? Склеивает ли Y-сортировка части одного атласа, не проверено; проверять первым в 2052 или 2054 (prototype ш.2; М-1).
3. Обводка и ауры: шейдер на спрайте, `CanvasGroup` только на выбранную цель, или отдельный проход одним батчем? (scene п.11 против prototype ш.2 и М-1).
4. Свет: `PointLight2D` в общем вьюпорте 960×540 (ступенчатый, дёшево, без теней); второй буфер для гладкого света; или свой проход (scene п.4, п.5, П2; prototype ш.2, вывод 4). Сравнение картинки с JS «с глаза» остаётся игроку.
5. Вращающиеся части рига (П1): nearest, линейная фильтрация с мипкартами как в прототипе, или перерасчёт голосованием (scene п.7; prototype ш.2).
6. Нужен ли рендерер Mobile для новых устройств (Metal 3, Vulkan) как дополнение к Compatibility, или Compatibility везде? Выигрыш для 2D не мерили; на iPad 6 Mobile не запускается (prototype ш.1, ш.2).

## 4. Что переносится как есть, что переписывается, что выбрасывается

Переносится как есть (по данным и смыслу):

- Содержимое данных: биомы, враги, предметы, аффиксы, умения, мета, `BAL`, `QUESTS`, `SHOP`; через экспорт в JSON (data А-1).
- `docs/names|notes|talk`, уже JSON (tools R-7; data А-9).
- Арт `art/gen/*.png`, таблица шарниров `rigs.js` как данные, `softbones.json` (scene п.11; tools R-10; prototype ш.2).
- Алгоритмы ГСЧ и хешей: mulberry32, `qhash`, `mix32`, `bagOrder`, `layOf`, `modOf`, `wanderAt`, `stageOf` (sim P-1; data А-5).
- Порядок бросков и проверок отказа генератора (dungeon R11); логика стадий по таблице 6.2 как готовая спецификация (dungeon R4).
- Шейдеры лавы, воды, магмы, пещеры, фон и туман: GLSL ES 3.00 почти по тексту в `.gdshader` (scene п.6).
- Спецификации для UI: `KIT.PART`, карта экранов, `D.UI.*` как отправная раскладка, правила фокуса, `SETTINGS`, `TEST_RUNS`, `NEWS` (hud п.18).
- Профили бота (`novice|average|expert|mage|builder`) и их эталонные доли побед и смертей (2052; sim P-14).
- Метод замера прототипа (`drawn=`, `bench.txt`, по этапам, `--stress`) (prototype ш.2).
- Сами проверки `selfCheck` как спецификация поведения (sim P-15; dungeon R14).

Переписывается:

- Сим и генератор: из JS в чистый C# (сборки Sim, Dungeon, Data), с типизированным состоянием, шиной событий, пулами, `RunProfile` (sim P-1…P-12; dungeon R1, R4, R7).
- Сохранения: схема с версией, этаж целиком, атомарная запись (sim P-4; игрок 14.11).
- Отрисовка: `scene*.js` в узлы Godot, слои, шейдеры файлами, свет, туман, маски, риги с IK (scene п.1…п.11).
- HUD: `hud.js` в сцены экранов, тема, фокус, `InputMap`, глифы (hud п.1…п.15).
- Тексты: в `tr()` и ключи, без готовых строк в состоянии (data Б).
- Функции в таблицах данных: формулы или `Balance` (data А-2); мини-язык сил: перечисления и обработчики (data А-4).
- Инструменты: проверки в тестовые проекты C# с реестром `[Check]`; бот с `IBotView`; фабрика сценариев; golden-файлы (tools R-1…R-9).
