### Ошибки и их решения (в порядке появления)

1. `CS0104: 'Environment' is ambiguous between Godot.Environment and System.Environment`: в `Main.cs` нужен `System.Environment`. Обычная коллизия имён Godot.
2. Экспорт Android: `Требуется указать верный путь к Java SDK в настройках редактора`. Пришлось записать `export/android/java_sdk_path` в `~/Library/Application Support/Godot/editor_settings-4.7.tres` (резервная копия до правки лежит в scratchpad сессии). Переменные окружения Godot для Java SDK не читает. Хранилище ключей отладки задано переменными `GODOT_ANDROID_KEYSTORE_DEBUG_*` на `~/.android/debug.keystore`.
3. Экспорт Android: `Для экспорта под Android требуется сжатие текстур ETC2/ASTC`: в `project.godot` добавлено `textures/vram_compression/import_etc2_astc=true`.
4. `xcodebuild` для симулятора: `IPHONEOS_DEPLOYMENT_TARGET is set to 14.0, but the range of supported deployment target versions is 15.0 to 27.2.x`. Xcode 27 не собирает ниже iOS 15: в пресете `min_ios_version="15.0"`. На iPad 17.7.11 это не мешает.
5. iOS simulator, линковка: `Undefined symbols for architecture arm64: "_main"`. Причина: в официальном шаблоне слайс `ios-arm64_x86_64-simulator/libgodot.a` содержит только x86_64 (`lipo -info`), что совпадает с оговоркой в документации Godot. Сборка с `ARCHS=x86_64` проходит, но установка в симулятор iPad (A16, iOS 27.2) отклоняется: «Необходимо обновить ElderDeep. Это приложение должно быть обновлено разработчиком для работы под управлением этой версии iPadOS» (x86_64-приложения этой версии симулятор не принимает). Итог: на Mac с Apple Silicon с Xcode 27 запускать iOS-сборку в симуляторе без собственного arm64-шаблона Godot нельзя. Для проверки на симуляторе потребовалась бы сборка шаблона из исходников; не делалась, потому что есть реальный iPad.
6. Запуск на iPad: `devicectl device process launch` вернул `Security: Unable to launch dev.elderdeep.proto01 because it has an invalid code signature, inadequate entitlements or its profile has not been explicitly trusted by the user`. Подпись при этом валидна (`codesign --verify --deep --strict` без ошибок, профиль выпущен автоматически на Personal Team, `get-task-allow=true`); причина в том, что профиль бесплатной Personal Team не доверен на устройстве. Без действия игрока дальше не пойти.

### Краш на iPad и его причина (14.11.2026, итог)

После доверия профиля приложение на iPad запустилось и сразу упало (`dev.elderdeep.proto03`, рендерер Mobile):

- `devicectl ... launch --console -- --verbose` (первые два запуска без вывода, с аргументом и подробным логом вывод появился):
```
[engine] Godot Engine v4.7.2.stable.mono.official.ed1daf0bf
[ERROR] drivers/metal/rendering_device_driver_metal3.cpp:107:initialize(): Condition "err" is true. Returning: err
[ERROR] servers/rendering/rendering_device.cpp:8376:initialize(): Failed to initialize driver for device.
[ERROR] main/main.cpp:3390:setup2(): Unable to create DisplayServer, all display drivers failed.
[ERROR] main/main.cpp:4017:start(): Condition "!_start_success" is true. Returning: 1
App terminated due to signal 11.
```
- Краш-логи с устройства (`devicectl device info files / copy from --domain-type systemCrashLogs`): `EXC_BAD_ACCESS (SIGSEGV)`, `KERN_INVALID_ADDRESS at 0x120`, главный поток: `pthread_mutex_lock` <- `std::recursive_mutex::lock` <- `Input::set_gravity` <- `-[GDTView handleMotion]` <- `-[GDTView drawView]`. То есть движок не поднялся (нет DisplayServer), `Input` уничтожен, а display link ещё вызывает `handleMotion` с нулевым указателем. Первый запуск до этого завершился с кодом 0, второй с сигналом 11. Образы в логе: только `ElderDeep` (NativeAOT-библиотека `ElderDeep.framework` загружается в процесс), к C# падение не относится.
- Причина: на iPad 6 (A10, iPadOS 17.7.11) не инициализируется драйвер Metal 3, который использует рендерер Mobile (Forward Mobile). Подтверждено логом выше.
- Исправление (одна гипотеза, один раз): в `project.godot` `renderer/rendering_method` и `renderer/rendering_method.mobile` стали `gl_compatibility`, `config/features` с «GL Compatibility»; чистый экспорт, `xcodebuild`, установка, запуск. Результат: `Setting up an OpenGL ES 3.0 context.`, приложение живёт без падений минимум 60 с (процесс завершён моим тайм-аутом, сигнал 15), второй запуск 25 с тот же итог. Игрок подтвердил, что приложение на iPad запустилось и не вылетает.
- Что в консоли iPad не видно: строк `C# RUNNING` и `CSHARP_OK` нет. `GD.Print` на iOS в этом режиме консоль `devicectl` не отдаёт (системные сообщения `[engine]` и `[ERROR]` отдаёт). Доказательство выполнения C# на iPad, кроме экрана (его видит игрок), не получено. Чтобы снять и это, можно добавить в `Main.cs` вызов `GD.PushWarning` (идёт через ту же трубу, что и `[ERROR]`); не делалось по указанию не пересобирать.
- Обратите внимание: Android-сборка экспортирована с Mobile (Vulkan), iOS уже с Compatibility; для замеров на старом iPad нужен Compatibility, для новых iPhone Mobile (Metal 3) скорее всего заработает, не проверено.

## Шаг 2: герой с ригом, комната со светом и туманом, 100-200 врагов, замеры

Дата: 14.11.2026. Задача 2053, шаг 2. Это прототип для замера, не порт. Код: `Main.cs` (сцена, свет, туман, HUD, джойстик, прогон замеров), `Rig.cs` (рига из частей и поза), `RigData.cs` (шарниры `hero` и `skeleton`, выгружены скриптом из `live/rigs.js`) в `elderdeep-godot/`; части и текстуры скопированы в `elderdeep-godot/art/` (не симлинки). Игра JS не менялась.

### Что собрано

- **Сцена целиком строится в C#**, одна сцена `Main.tscn` с корнем `Control`. Мир живёт в `SubViewport` 960x540; его текстура выводится `TextureRect` с фильтром nearest, режим «по центру с сохранением пропорций» (на экране 20:9 и 4:3 по бокам поля). HUD, кнопки и джойстик в `CanvasLayer` на полном разрешении, поверх. Моделируется сетка 2x2 из `study/refactor2/scene.md`.
- **Герой и скелет-враг с ригом**: `Sprite2D` на каждую часть (тот же холст, что в `art/gen`, `centered=false`), `Node2D`-шарнир с pivot из `rigs.js` (бедро, колено, лодыжка, плечо, локоть; у скелета ещё череп). Иерархия: бедро - голень - стопа, плечо - предплечье. Порядок отрисовки как в `scene_hero.js`: дальняя рука, дальняя нога, ближняя нога, тело, ближняя рука. Поза: ходьба (колебание бедра, колено сгибается на заднем шаге, руки навстречу, подпрыгивание), взмах ближней рукой (замах, удар, возврат) с клинком из `Polygon2D`. От JS-позы это малая часть: без IK колен, без плана шага, без капюшона и плаща на мягких костях, без оружия из игры. Герой 42 px высотой (84 px вида 1920x1080 из `sizes.js` пополам), скелет 38 px.
- **Y-сортировка**: `YSortEnabled` на узле мира, герой, враги и пропы прямые дети, начало узла у ног.
- **Комната** 80x45 тайлов по 16 px (1280x720): пол `floor_d_tex` плиткой (`Sprite2D` с `region` и повтором), стены `wall_d_tex` и `walltop_d_tex`, 9 ящиков и 8 бочек (`crate`, `barrel` из `live/assets/`), 6 факелов `torch_stand` с `PointLight2D` (тёплый цвет, текстура-градиент 256 px, без теней, лёгкое мерцание из кода) и огонёк-спрайт с аддитивным смешиванием, один свет на герое, `CanvasModulate` как ambient. Размеры пропов взяты из `sizes.js`.
- **Туман войны**: полноэкранный `ColorRect` с шейдером (затемнение по расстоянию до героя в пикселях вьюпорта), камера со снапом позиции к целым пикселям. Памяти исследованных клеток нет.
- **Враги**: до 400 скелетов с ригом (12 спрайтов на врага) предсозданных, подключаются к миру по числу (0 / 50 / 100 / 200; клавиши 1-4 или кнопка «Enemies»). Каждый идёт к своей точке на орбите вокруг героя, ходьба по позе рига; боя нет, столкновений между врагами нет. Режим «упрощённый спрайт» (один `skeleton.png` с покачиванием) переключается кнопкой Rig или клавишей M, свет клавишей L, туман клавишей G, взмах героя пробелом или кнопкой Swing.
- **Управление**: WASD или стрелки; на телефоне экранный джойстик (левые 40 % экрана, плавающий) и кнопки справа сверху. Нажатие кнопки проверено на Pixel 7 (`adb shell input tap` по «Light» выключил свет); джойстик на устройстве не проверялся (в режиме `--auto` героем управляет бот).
- **HUD**: FPS, время кадра, время скрипта (`Stopwatch` вокруг моего `_Process`), `cpuRender` (`RenderingServer.ViewportGetMeasuredRenderTimeCpu` по двум видовым экранам), draw calls и число объектов (`RenderingServer.GetRenderingInfo`), память Godot (`OS.GetStaticMemoryUsage`) и видеопамять (`VideoMemUsed`).
- **Прогон замеров** (`--auto`): 6 этапов по 33 с (3 с прогрев, 30 с замера): 0, 50, 100, 200 ригованных, 200 упрощённых, 200 ригованных со светом выключенным (ambient и все `PointLight2D` убраны, туман остаётся). ### Что показали замеры

1. **Кадр упирается в CPU (подача draw calls), не в GPU.** В одном потоке `script + cpuRender` почти точно равно кадру: iPad, 300 врагов 2,94 + 15,98 = 18,9 мс при измеренных 19,8; 400 врагов 3,81 + 23,79 = 27,6 при 28,6. Цена одного draw call: iPad 4,4 мкс, Pixel 7 3,9 мкс, M3 Max 3,1 мкс (на Mac Godot тоже упирается в подачу команд, а не в GPU). Из этого: слабое место - число draw calls, а не пиксели, размер фрагментного шейдера или свет.
2. **Рига из 12 отдельных текстур даёт около 12 draw calls на врага** (200 врагов: 2460 draw calls). Y-сортировка перемешивает части разных врагов, текстуры чередуются, склейка (batching) не срабатывает. Тот же 400 врагов одним спрайтом (одна текстура): 71 draw call, на iPad 4 мс вместо 24. Это самая важная цифра прототипа. Гипотеза (не проверена, оптимизации заранее не делал): если все части героя и монстров свести в один атлас (или в один на тип), части склеятся и draw calls упадут к сотне. Проверить первым делом в 2052/2054.
3. **Свет почти бесплатный на Compatibility.** 7 `PointLight2D` плюс `CanvasModulate` по сравнению со светом выключенным: Pixel 7 9,57 против 9,19 мс cpuRender, iPad 10,77 против 10,84, draw calls те же (2460 и 2461): свет считается в шейдере элемента, а не дополнительными проходами. На Mac 7,6 против 5,8 мс (с шумом от параллельных прогонов). Теней, больше 7 источников и свет разного размера не пробовал.
4. **Запас на слабом железе.** При 200 ригованных врагах кадр занимает 12-13 мс из 16,7 на Pixel 7 и iPad 6. В игре на экране обычно около 70 монстров (сцены из `study/refactor2/summary.md`); по таблицам это 6-9 мс (script + cpuRender). Но это без пост-прохода (оценка, виньетка, дизеринг), без FX заклинаний, без HUD игры, без симуляции, с одним типом монстра. Запас под всё это на iPad 6 есть только при условии, что draw calls рига сведены вниз (см. п. 2).
5. **C# не стал узким местом.** Скрипт (моя поза и движение 200-400 ригов, около 8 присваиваний `Rotation` на риг за кадр через интероп) 0,1-3,8 мс (на 200 врагах: iPad, NativeAOT, 2,5 мс; Pixel, Mono, 2,6; Mac, CoreCLR, 0,7). Куча C# 6-21 МБ, заминок от сборщика мусора не видно (p99 равен 16,67 мс в стабильных этапах).
6. **Сравнение с JS** (`study/refactor2/summary.md`: JS-кадр 3,6-7,3 мс на M3 Max на 70 монстрах, на Deck в 4-5 раз дороже, 18-22 мс). Godot на том же M3 Max: 100 врагов 3,8 мс (script + cpuRender), 200 врагов 8,3 мс, то есть тот же порядок, при том что в JS кадр ещё содержит 2 шага симуляции и больше картинки. На Pixel 7 и iPad 6 (cpuRender в 1,5-3,5 раза выше, чем на Mac: Godot на Mac идёт через OpenGL поверх Metal) 100 врагов 8-10 мс, 200 врагов 12-13 мс. Если Deck по подаче draw calls близок к этим двум (предположение: Deck не мерял), 60 FPS на нём при 200 врагах держится с малым запасом, а при 70 монстрах с хорошим. Цифру нужно снять.

### Что Godot даёт готовым, что пришлось делать руками

Готовое: иерархия `Node2D` с шарнирами и Y-сортировка без кода; `PointLight2D`, `CanvasModulate`, плитка с повтором; `SubViewport` и масштаб nearest одной настройкой; мипкарты через `importer_defaults` в `project.godot` (одна строка); счётчики `RenderingServer.GetRenderingInfo` и замер времени рендера видового экрана; эмуляция мыши из касаний (кнопки на Pixel 7 откликнулись без кода); экспорт Android, iOS, Windows и Linux из одной консольной команды; пакет .NET встроен в экспорт Windows и Linux (самодостаточный).

Руками: поза рига и ходьба (около 150 строк `Rig.cs`), перенос шарниров из `rigs.js` (скрипт в `RigData.cs`), туман (6 строк шейдера), текстура света (градиент в коде), плавающий джойстик (около 20 строк), прогон замеров и запись результатов в файл, проверка «окно реально отрисовывается».

### Ловушки замеров (чтобы не потерять время снова)

- **Закрытое или спящее окно Mac не рисуется.** Godot пропускает рендер окна, которое macOS считает закрытым (экран гаснет, заставка, окно под другим). Строки `draw calls` и `objs` при этом замирают на значениях пустой сцены, а кадр держится на 144-145 FPS: это ложный замер. Поэтому в результат добавлено `drawn=` (доля реально отрисованных кадров); значения меньше 100 % не брать. Помогли `--always-on-top`, `caffeinate -d` и запуск этапов по одному; полностью не гарантировано, если игрок отошёл от Mac.
- **Консоль iOS не отдаёт строки C#.** `GD.Print`, `GD.PushWarning` и `GD.PushError` на iPad не доходят до `devicectl --console`, хотя C++-ошибки движка доходят. Чтение из `Documents/bench.txt` приложения (команда выше) работает.
- **Первый запуск на устройстве холодный** (шейдеры компилируются): на iPad первые этапы дали 57-59 FPS против 60 после прогрева.
- **`dumpsys gfxinfo`, `Performance.Monitor.TimeProcess` и `gpuRender` дают нули или мусор** на Compatibility; GPU-время получить штатно нельзя, вывод о том, что упор в CPU, сделан по сумме `script + cpuRender` и по стоимости draw call.
- Параллельный чужой прогон на Mac менял результаты на 25 %; на Android и iPad повторы совпадали до сотых миллисекунды.

### Не получилось и что не сделано

- **Steam Deck и слабый Windows-ПК**: у меня их нет, замеров нет. Сборки для них готовы (см. ниже), снимает игрок.
- **Тепло iPad 6**: см. выше, снимает игрок по ощущению; программно недоступно.
- **GPU-время**: не получить на Compatibility; оценено косвенно (п. 1).
- **`CanvasGroup` для обводки**: не собрано, не измерено. Ожидаемо дорого: каждая группа рисуется в отдельный буфер; не делать `CanvasGroup` на каждого монстра, обводка нужна шейдером на спрайте или группой на одну выбранную цель.
- **Два буфера (мир nearest 960x540 и свет билинейный, см. `scene.md` п. 1 и П2)**: не собрано; свет в прототипе рисуется внутри того же вьюпорта 960x540, поэтому он такой же ступенчатый, как мир, а не гладкий, как в JS. Это отдельный риск 2052.
- **Повторная растеризация вращающихся частей (`snapTex`, П1)**: не делал; части рига рисуются с линейной фильтрацией и мипкартами в 960x540, по скриншотам читается нормально. Сравнение «с глаза» с JS остаётся игроку.
- **Мягкие кости привидения (`Polygon2D` и `Skeleton2D`)**, **IK колен**, **тени**, **Mobile-рендерер** (на iPad 6 он не поднимается; на Pixel 7 мог бы, не проверял), **release-сборки** (всё в debug, release быстрее, сколько - не знаю), **батарея и расход**.
- **Сборки Windows и Linux не запускались** (нет таких машин). Экспорт прошёл без ошибок, но проверено только то, что файлы собраны.
- Mac: этап 400 врагов на Mac помечен ненадёжным (отрисовано 89 % кадров).

### Вывод и риски для 2052

1. **Мобильные цели достижимы на Godot 4.7 + C# + Compatibility.** Pixel 7 держит 60 FPS до 400 ригованных врагов, iPad 6 (A10, нижний край) 60 FPS до 200 и 35 FPS на 400. C# (Mono на Android, NativeAOT на iOS) не стал узким местом.
2. **Compatibility вместо Mobile - по умолчанию.** Mobile на A10 не поднимается (Metal 3), на Android Vulkan. Всё сделано на Compatibility, всё работает; Выигрыш Mobile для 2D я не измерял, а на iPad 6 он не запускается. Закладывать Compatibility как базу, Mobile как возможное дополнение для новых устройств.
3. **Главный риск - число draw calls.** Рига из отдельных текстур даёт 12 draw calls на монстра. Архитектура 2052 должна заранее хранить части в атласе и проверить, что Y-сортировка склеивается; бюджет на целевое слабое железо: около 2500 draw calls на кадр при 60 FPS (iPad 6: 13 мс; Pixel 7: 12 мс), 1250 на запас. Спрайт на монстра без рига (дальняя дистанция, толпа) стоит почти ничего.
4. **Свет `PointLight2D` на Compatibility годится**; ограничение - ступенчатость в 960x540 и отсутствие теней. Если нужен гладкий свет, как в JS, нужен второй буфер или отдельный проход (не проверен).
5. **`SubViewport` 960x540 nearest** работает просто и дёшево; рамка 16:10 и масштаб ZOOM из `scene.md` не проверялись.
6. **`CanvasGroup` для обводки**: не использовать на каждом монстре, пока не измерено.
7. **Метод замера** (счётчик `drawn=`, файл `bench.txt`, запуск по этапам, `--stress`) пригоден и переходит в порт; проект замеров лежит в `elderdeep-godot/`, коммитить его в `game-demo` не нужно, решение «основа порта или выбросить» остаётся игроку.
